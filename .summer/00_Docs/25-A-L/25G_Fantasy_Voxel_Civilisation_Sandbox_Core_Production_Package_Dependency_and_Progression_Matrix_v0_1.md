# Document Purpose

Document 25G is the dependency proof for the first post-POC production slice. Document 25F selected the Core world, civilisation, ecology, adventure, realm and infrastructure foundations. This document determines whether those selections can operate as complete packages rather than disconnected names. It records what each package requires, offers, consumes, produces, changes, presents, saves, simulates and validates.

By instructing the project to proceed from 25F to 25G, Ash has accepted Document 25F as the current working scope lock. That approval freezes ungoverned Core intake but does not prevent a recorded substitution, reduction or correction under 25A and 25F change control.

25G does not create final block, item, resource or recipe IDs; those belong to 25H-25J and the replacement versions of Documents 03-06. It does not define Godot classes, numeric performance budgets or changed files; those belong to rewritten Document 18 and 25L. It does not design maritime gameplay; Set 26 remains the authority for oceans, vessels and naval systems.

# 1. Locked Package Dependency Identity

> [!locked] **Locked Rule**  
> A Core Production package is not complete because its Atlas entry, model, biome, creature or mechanic exists. It is complete only when its required providers, capability role, physical inputs and outputs, fallbacks, world-state effects, presentation, save/LOD/authority treatment and acceptance evidence are all explicit and mutually valid.

| Identity Layer | 25G Meaning | Player-Facing Result |
| --- | --- | --- |
| Package, not list | Related foundations ship and validate as a coherent functional unit. | The world does not contain beautiful but useless or unreachable content. |
| Capability progression | Progress is guaranteed through provider categories and alternatives. | Seeds differ without silently blocking survival, automation, magic or realm access. |
| Physical conservation | Atlas roles must resolve to real block/item/resource/recipe transactions. | Production, settlement supply and rewards remain tangible and trustworthy. |
| Persistent consequence | Events, sites and threats change stored world state. | Exploration and civilisation decisions leave visible aftermath. |
| Bounded production | A package has a ceiling, owner, risk and deferral trigger. | Core proves the final identity without becoming the whole Atlas. |

# 3. Scope, Non-Goals and Handoff Boundaries

## 3.1 In scope

- qualified package identities and package ownership;
- required/optional dependencies and cycle prevention;
- capability providers, requirements, substitutions and repair rules;
- provisional physical input/output classes for later registry definition;
- cross-system relationships, persistent states and presentation obligations;
- full/reduced/abstract simulation, save, migration and authority classes;
- exact 24/14/36/18 narrative foundation roster promised by 25F;
- validation suites, seed coverage, risks, blockers and deferral triggers;
- handoffs to 25H-25L, revised Documents 03-18 and Set 26.

## 3.2 Explicit non-goals

- final material statistics, recipes, drops, station times or economic values;
- final terrain palettes, models, textures, rigs or animation lists;
- complete quest dialogue, boss mechanics, AI behaviour trees or settlement layouts;
- Godot node/class/file architecture or Summer Engine implementation tasks;
- full ocean, fluid, vessel, port, fleet or naval-combat design;
- promotion of Early Access, Full Release or Tooling Research content into Core.

# 4. Canonical Package Terminology

| Term | Meaning |
| --- | --- |
| Core Package | A governed group of definitions and contracts that ships and validates as one production responsibility. |
| Provider Package | Offers a declared capability, physical output, service, route, knowledge or state transition. |
| Consumer Package | Requires a capability or definition and declares acceptable provider criteria. |
| Hard Dependency | Package cannot compile, generate or function without the provider in the active build profile. |
| Soft Dependency | Adds valid enrichment; absence uses declared omission or fallback. |
| Profile Dependency | Required only for a particular world/build profile. |
| Runtime Dependency | Generated instance relationship selected by the seed or later world state. |
| Fallback Group | Ordered or weighted alternatives capable of satisfying the same requirement. |
| Repair Action | Deterministic generation or runtime response when eligible providers are absent. |
| Dependency Debt | Missing decision, ID, system contract, asset family, validator or runtime proof that blocks a later status. |
| Conditional Package | Scope remains selected, but implementation entry is blocked until named debt closes. |

# 6. Dependency Classes and Cycle Rules

| Rule | Requirement |
| --- | --- |
| No circular hard dependencies | A package graph with a hard cycle fails compilation and planning approval. |
| Capabilities over named content | Survival, magic, trade, adventure and realm access depend on provider queries, not one named entry. |
| Base cannot hard-reference optional expansion | Core may expose extension interfaces but Set 26-owned IDs remain optional unless a build profile promotes them. |
| Physical definitions precede implementation | No Integrated package may rely on placeholder resources, drops or recipes. |
| Runtime links use instance identities | Generated settlement, boss, route and site relations bind to persistent instances, not definition IDs alone. |
| History cannot invent participants | Events wait, substitute by role query or omit rather than create absent named actors/places. |
| State does not mutate identity | Damage, ownership, season, corruption, occupation and restoration use state/profile records. |

# 7. Capability Bands and Progression Graph

| Band | Capability | Required Proof |
| --- | --- | --- |
| CAP-00 | Safe Spawn and Local Survival | Food/water-access equivalent, immediate shelter material, fuel/light path and safe construction area. |
| CAP-01 | Primitive Tools and Shelter | Hand gathering, basic work surface, common tool heads, repair and simple storage. |
| CAP-02 | Provisions and Settlement Contact | Renewable food, health/medicine input, route clue, trade or settlement discovery. |
| CAP-03 | Copper Mechanisms | Copper or equivalent conductive/mechanical material, gears/plates, simple power and logistics. |
| CAP-04 | Iron Structural Support | Iron or capability-equivalent durable tool/structure material, forge/refinement and settlement project support. |
| CAP-05 | Practical Mana | At least two valid discovery/provider families for mana, runes, wards, cleansing or magical power. |
| CAP-06 | Regional Trade and Civilisation | At least two cultures, settlement services, route access, warehouse permissions and lawful/alternative exchange. |
| CAP-07 | Regional Adventure | Reachable site, threat warning, suitable counterplay, rewards and safe exit/aftermath. |
| CAP-08 | Automation-to-Civilisation | Resource-conserving production chain supplies a settlement need, project, defence, trade or recovery outcome. |
| CAP-09 | Realm Discovery and Safe Return | Knowledge/material/relationship route, stable arrival, return class, rescue fallback and persistent route record. |
| CAP-10 | Verdant Realm Resolution | Realm society/ecology/site/authority path with several outcomes and Overworld-visible aftermath. |

The intended capability graph is branching rather than a linear material ladder:

> [!info] **Capability Flow**  
> CAP-00 Safe Spawn -> CAP-01 Primitive Tools -> {CAP-02 Provisions/Civilisation, CAP-03 Copper Mechanisms} -> {CAP-04 Iron Support, CAP-05 Practical Mana, CAP-06 Regional Civilisation} -> {CAP-07 Adventure, CAP-08 Automation-to-Civilisation} -> CAP-09 Realm Access -> CAP-10 Verdant Resolution.

A seed may satisfy a later capability through trade, salvage, research, restoration, culture teaching or realm materials when the physical and knowledge requirements are valid. No capability is awarded merely because the player reaches a level.
