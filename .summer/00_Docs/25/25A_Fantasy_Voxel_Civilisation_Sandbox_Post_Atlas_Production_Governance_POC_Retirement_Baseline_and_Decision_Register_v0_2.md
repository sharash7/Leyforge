# Document Purpose

This document begins Document Set 25 and establishes the control layer for the entire post-Atlas production phase. It turns the Atlas roadmap into an auditable production baseline before registry expansion or implementation begins. Its purpose is to ensure that the project does not carry demonstration-only assumptions into production, does not confuse Atlas breadth with implementable scope, and does not allow duplicate or unsupported source-of-truth definitions to emerge during revision. Version 0.2 also establishes how a separately owned major expansion, Document Set 26, may develop alongside the production spine without duplicating maritime design inside Set 25 or bypassing its registry, packaging, migration, validation and release controls.

Document 25A does not select the final Core Production content roster, define machine-readable schemas, rewrite the Technical Plan, enumerate the new Blocks and Items registries, or design oceans, vessels, maritime civilisation or naval combat. Those responsibilities belong to later Set 25 documents, replacement versions of the main design documents and Document Set 26. This document defines the governance conditions under which that work may proceed and later be integrated.

# 1. Locked Production Governance Identity

The post-Atlas production programme is the conversion layer between world design and an implementable game. Its role is to transform selected Atlas foundations into validated registries, Godot data, seed-generated worlds, assets, simulation, interface and persistent player-facing consequences without returning to hardcoded demonstration content. It is also the admission spine through which separately owned major expansions can become compatible, save-safe and releasable without being absorbed into Set 25.

> **Locked Governance Rule**  
> No content package advances because it has an appealing name, model, texture, prose description, or isolated mechanic. Advancement requires stable identity, canonical ownership, complete relationships, physical support, fallback behaviour, asset and presentation requirements, runtime bindings, save/migration treatment, validation evidence and recorded approval.

> **Locked Major-Expansion Rule**  
> Approval of a document set does not exempt its content from Set 25 governance and does not automatically assign a shipping tier. Document Set 26 remains a separate system-design authority, while each maritime package must still pass identity, dependency, classification, migration, validation and release-admission gates.


| Identity Layer | Governance Meaning | Production Result |

| --- | --- | --- |

| Clean Production Baseline | POC identities and fixed arrangements are isolated from normal generation and active dependencies. | Production decisions cannot silently fall back to the old demonstration. |

| Canonical Authority | Every rule, field and definition has a named owner and supersession path. | Conflicts are visible and duplicate editable truth is rejected. |

| Approved Scope | Atlas foundations are classified before physical or asset expansion. | The first slice proves final-game identity without trying to implement the whole Atlas. |

| Evidence-Based Status | Lifecycle advancement requires data, tests, assets and integration evidence. | Planning volume is not mistaken for playable completion. |

| Safe Change | IDs, packs, saves, migrations and dependencies are reviewed before revision or removal. | Existing production worlds remain recoverable and updates are explainable. |

| Human Authority | AI and tools may assist drafting, analysis, validation and implementation, but final approval remains human. | Scope, canon, representation, licensing and release decisions remain accountable. |

| Expansion-Capable Spine | Major expansion sets use shared IDs, ownership, packs, validators, saves and release gates while retaining their own detailed design documents. | Set 26 becomes the first real extension case without hardcoding maritime rules into the kernel. |

A POC element does not survive merely because it is convenient, already implemented or visually complete. # 11. Supersession, Versioning and Change Control

> **Change-Control Rule**  
> A later document does not supersede an earlier rule merely by being newer. Supersession must identify the old source, exact affected rule, reason, replacement authority, compatibility effect, migration requirement and approval record.


| Change Class | Examples | Required Review |

| --- | --- | --- |

| Editorial | Clarity, spelling, formatting, cross-reference correction with no design effect. | Documentation review; no architecture decision. |

| Design Clarification | Resolves ambiguity without changing player-facing scope or technical contract. | System owner and source-owner review. |

| Design Change | Changes progression, survival, content role, world behaviour, player choice or package completeness. | Ash approval and dependency review. |

| Schema Change | Adds/removes/changes fields, types, cardinality, ID grammar or relationships. | Architecture decision, migration plan, validator update and reverse-reference report. |

| Content Change | Adds, removes, replaces or reclassifies a production definition. | Package owner, dependency and asset impact review. |
