**Version 1.0 - Reconciled Production Foundation Draft**  
**Date:** 8 August 2026  
**Supersedes:** `01_Fantasy_Voxel_Civilisation_Sandbox_Core_Gameplay_Loop_v0_1.md` for active production direction

A production-scale gameplay-loop foundation for a fully seed-generated fantasy voxel civilisation sandbox where immediate physical actions create persistent consequences across survival, construction, automation, magic, social relationships, economy, settlements, travel, maritime play, ecology, conflict, realms and world history.

> **Core Loop Statement**
>
> **Explore -> gather -> craft -> build -> interact -> automate -> defend -> upgrade -> expand** remains Leyforge's broad sandbox loop, but it is not a mandatory sequence. The player may enter, leave, reverse or combine its stages according to world state, personal goals, available capabilities and chosen playstyle. Every meaningful loop should begin in authoritative world conditions, pass through real player or simulated actions, and end in a world response that can create the next opportunity, need, relationship, route, risk or ambition.

> **Production Loop Rule**
>
> **No normal world may require the retired proof-of-concept scenario, one fixed settlement, one fixed resource chain, one fixed ruin, one fixed enemy camp or one scripted threat sequence in order for the core game to function. Every seed must support multiple valid ways to enter and continue the game through generated relationships, substitute capabilities and discoverable alternatives.**

# Document Purpose

Document 01 defines **how Leyforge is played over time**. It translates the Master Game Design Bible into repeatable player-facing loops at the scale of seconds, minutes, days, journeys, settlement cycles, regional change and long-term sandbox history.

The original v0.1 document established several principles that remain correct:

- the game is sandbox-first;
- the broad loop is **Explore -> gather -> craft -> build -> interact -> automate -> defend -> upgrade -> expand**;
- the player should have multiple valid playstyles rather than one mandatory class or campaign route;
- guidance should be optional and configurable;
- worlds should be seed-generated;
- the game should have escalating goals without a fixed ending;
- survival, villages, automation, magic, exploration, combat, economy, settlements and realms should reinforce one another.

Version 1.0 preserves those principles while reconciling them with the production systems established after the original foundation was written. In particular, this revision integrates:

- Document Set 24's fully seed-generated Atlas topology, authored randomness, relationship graphs, procedural history and dynamic world states;
- Document Set 25's POC retirement, content classification, capability/fallback model, canonical registry governance and production validation;
- Documents 19-20's settlement growth, player blueprints, functional buildings, visible construction and seven-needs model;
- Sets 21-23's Unified Forge authoring direction where it affects player-created or production-created content workflows;
- Set 26's oceans, swimming/diving, vessels, ports, crews, maritime trade, salvage, naval danger and marine ecology;
- Set 27's physical, regional economy, markets, contracts, labour, finance, public works and trade-route economics;
- Set 28's dialogue, knowledge, rumours, relationships, social consequences, companions and delegation;
- Set 29's biological health, Stamina, Fatigue, hunger/hydration/nutrition, exposure, injury, disease and treatment;
- Set 30's movement, traversal, mounts, land vehicles, routes, accessibility, travel time and navigation;
- the final Sets 27-30 v1.1 ownership/interface reconciliation, including the resolved aquatic locomotion boundary between Set 26E and Set 30.

This document **does not own the formulas or runtime truth** of those specialist systems. Its role is to define how their outputs become coherent player loops.

# 1. Locked Gameplay Identity

Leyforge is a sandbox where **doing something useful should create another meaningful possibility**.

The game is not structured around clearing a linear mission list. It is structured around a changing world that continually presents:

- needs;
- opportunities;
- resources;
- relationships;
- routes;
- threats;
- discoveries;
- ambitions;
- consequences.

The player chooses what matters next.

A settlement shortage can become a farming problem, a trade problem, a transport problem, a diplomatic problem, a construction problem, a magical problem or an automation problem. A blocked mountain route can become a climbing challenge, a road project, a bridge project, a mount decision, a caravan delay, an economic shortage, a social request or an exploration detour. A dangerous coastline can become a vessel-upgrade goal, a navigation challenge, a port-development project, a fishing opportunity, a salvage expedition or a regional trade route.

> **Locked Gameplay Rule**
>
> A strong Leyforge loop does not merely give the player a task. It gives the player a **reason**, multiple plausible **methods**, an authoritative **result**, and a persistent **world response**.

## 1.1 What the Player Is Repeatedly Doing

Across the entire game, the player repeatedly performs five high-level acts:

1. **Read the world.** Notice need, opportunity, danger, information or curiosity.
2. **Choose an intention.** Decide what outcome matters and how much risk or effort is acceptable.
3. **Assemble capability.** Gather knowledge, people, resources, equipment, routes, permissions, infrastructure or magic.
4. **Act.** Travel, build, trade, negotiate, fight, automate, heal, research, explore, command or create.
5. **Receive consequence.** The world changes, records the outcome and exposes the next decision.

This five-part cycle sits underneath every specialist loop in this document.

# 2. Core Loop as a Network

The original broad loop remains production-valid:

> **Explore -> gather -> craft -> build -> interact -> automate -> defend -> upgrade -> expand**

However, it must be understood as a **network of verbs**, not a conveyor belt.

| Loop Verb | Typical Entry Question | Example Outcomes |
| --- | --- | --- |
| **Explore** | What is here? Where can I go? What is happening? | Discover resources, people, routes, sites, rumours, threats, markets, realms or opportunities. |
| **Gather** | What physical inputs do I need? | Acquire raw materials, food, salvage, samples, relics, cargo or biological resources. |
| **Craft** | How do I turn resources into capability? | Tools, equipment, components, medicines, supplies, structures, magical or transport parts. |
| **Build** | What physical change will solve or enable something? | Shelter, roads, workshops, farms, defences, ports, machines, homes, public works, vessels. |
| **Interact** | Which people, institutions or systems matter? | Trade, talk, recruit, negotiate, teach, learn, request, threaten, ally, contract, govern. |
| **Automate** | What repeated work should scale beyond hand labour? | Processing, hauling, farming, logistics, power, mana, settlement supply and industrial chains. |
| **Defend** | What is at risk and how can I protect it? | Fight, fortify, ward, evacuate, negotiate, scout, repair, reroute, insure or prepare. |
| **Upgrade** | What limitation should be removed next? | Better tools, knowledge, routes, buildings, machines, social access, transport, medicine, magic. |
| **Expand** | What new region, role, network or ambition becomes possible? | New settlement, trade route, sea voyage, faction role, realm route, industry or megaproject. |

## 2.1 Reverse and Sideways Loops

The player may move backward or sideways through this network.

Examples:

- **Interact -> Explore:** a rumour reveals an unknown ruin.
- **Trade -> Build:** profit funds a workshop or public road.
- **Build -> Social:** a community project increases access to people or institutions.
- **Defend -> Repair -> Automate:** a raid exposes a supply bottleneck that the player later automates.
- **Explore -> Treat -> Retreat:** a disease or injury turns an expedition into a recovery loop.
- **Sail -> Salvage -> Craft -> Refit -> Sail:** maritime progression can cycle without touching settlement growth immediately.
- **Negotiate -> Contract -> Transport -> Market:** a social interaction can lead directly into economic and movement loops.

## 2.2 No Mandatory System Participation

Not every player must deeply engage every system.

A player may:

- trade casually without becoming a market specialist;
- use companions without micromanaging social optimisation;
- build roads without operating caravans;
- sail without becoming a naval power;
- survive with simplified biological settings;
- help settlements without ruling one;
- practice magic without building a magitech industry;
- automate only enough to reduce repetitive labour;
- avoid most combat through settings, preparation, diplomacy, stealth or route choice where supported.

The systems should still remain connected enough that specialists feel rewarded for understanding them.

# 3. The Universal Action-to-World-Response Cycle

Every important action should complete a readable causal loop.

## 3.1 State -> Intent -> Validation -> Cost -> Result -> Evidence -> Consequence

| Stage | Meaning |
| --- | --- |
| **State** | The world has an authoritative condition: stock, terrain, health, relationship, route, market, structure, threat, weather, ownership or knowledge state. |
| **Intent** | A player, NPC, settlement, machine or event requests an action. |
| **Validation** | Owning systems decide whether the action is possible, permitted and sufficiently supplied. |
| **Cost** | Real resources, time, effort, opportunity, risk, money, mana, biological capacity or social capital are committed where required. |
| **Result** | The owning system resolves the actual change. |
| **Evidence** | UI, animation, inventory, dialogue, construction, market state, map, route state, injuries or world geometry make the result observable. |
| **Consequence** | Other systems consume the new state and generate follow-on opportunities or problems. |

## 3.2 Why This Matters

Without this cycle, Leyforge risks becoming a set of disconnected menus. A village project should not complete because a progress bar reached 100% while the required materials never existed. A caravan should not arrive because an economic timer expired while the route is physically broken. A companion should not appear across the world because a dialogue choice said "follow me" if movement cannot reach the destination. A healing action should not restore biological state because a social actor wanted to help if the treatment was invalid.

The gameplay loop therefore depends on **cross-system evidence**, but each domain remains owned by one specialist.

# 4. Sandbox Freedom and Player Direction

Leyforge should give the player enough information to choose a direction without deciding that direction for them.

## 4.1 Sources of Player Goals

Goals can emerge from:

- immediate survival;
- curiosity;
- visible terrain or landmarks;
- settlement needs;
- requests or contracts;
- relationships;
- rumours and knowledge;
- market opportunities;
- shortages;
- threats;
- injuries or illness;
- transport barriers;
- construction ambitions;
- automation bottlenecks;
- magical research;
- faction politics;
- ecological change;
- maritime opportunity;
- realm access;

## 4.2 Self-Directed Goals Are First-Class

The quest journal must not be the only place where legitimate goals exist. A player who decides to build a mountain road, found a fishing village, create a glass industry, breed mounts, map an archipelago, restore a ruin, establish a trade company or build a magical transport network is participating in the core game even if no authored quest requested it.

- rumours;
- map notes;
- codex links;
- recipe hints;
- route warnings;
- biological condition explanations;
- market explanations;
- companion suggestions;
- player-pinned goals.

Players may reduce or disable most guidance without losing access to authoritative state.

# 5. Seed-Adaptive New World Start

A production world must not begin by recreating the retired POC valley under another name.

The opening experience is generated from:

- world seed;
- enabled content packs;
- production classification;
- world settings;
- region topology;
- biome and climate;
- nearby resource families;
- settlement/site relationships;
- routes and barriers;
- ecology and danger;
- local histories;
- capability substitutions.

## 5.1 Starting Principle

The player begins with limited capability and enough local possibility to form a plan.

The world does **not** need to guarantee one exact village, cave, ruin, ore vein or quest. It must instead guarantee that the player can reach required capability categories through one or more valid routes.

Examples:

- if a particular starter material is absent, an approved substitute family can satisfy the capability;
- if no settlement is immediately visible, roads, rumours, landmarks, travellers, maps or exploration can reveal civilisation later;
- if a route is blocked by terrain, alternative movement modes, construction, detours or later infrastructure may solve it;
- if one knowledge source is absent, another NPC, book, ruin, experiment or cultural source may teach the capability.

## 5.2 Spawn Experience

A normal opening should communicate:

- biome and weather character;
- immediate terrain readability;
- basic gatherable resources;
- a reason to move or investigate;
- at least one short-term survival option;
- at least one visible or discoverable medium-term opportunity;
- no dependency on a single canonical tutorial NPC or settlement.

# 6. First Minutes and Early Survival

The opening should preserve the tactile pleasure of being small in a large world.

Typical early actions include:

1. orient to terrain, weather and time;
2. gather locally available starter resources;
3. create or locate basic shelter, tools, food and light as required by world settings;
4. inspect the environment for routes, water, resources, structures, smoke, tracks, roads, coastlines, caves, ruins or other signs;
5. decide whether to establish locally, travel, follow civilisation, investigate danger or seek a particular material;
6. begin discovering the world's specific relationships rather than following a fixed script.

## 6.1 Early-Game Readability Rule

The player should not need advanced UI knowledge to survive the opening. The physical world, contextual interactions and optional guidance should reveal enough to act.

## 6.2 Configurable Biological Depth

Set 29 may make hunger, hydration, nutrition, temperature, wetness, sleep, injury and disease more or less demanding depending on world settings. Document 01 requires that:

- those pressures create understandable decisions;
- reduced settings do not remove unrelated progression systems;
- survival does not become constant interruption on default balanced settings;
- preparation should feel useful rather than bureaucratic.

# 7. Minute-to-Minute Physical Loop

The minute-to-minute loop is the tactile core of Leyforge.

| Activity | Player Experience | Typical Cross-System Connection |
| --- | --- | --- |
| Move | Walk, sprint, climb, swim, glide, ride, drive or otherwise traverse readable terrain. | Exploration, combat, transport, biology, routes. |
| Observe | Read blocks, weather, creatures, people, structures, tracks, machines, water and hazards. | Knowledge, ecology, quests, social, survival. |
| Gather | Mine, chop, harvest, fish, salvage, loot, collect or trade for physical resources. | Crafting, economy, settlements, magic. |
| Craft | Transform resources into tools, parts, food, medicine, equipment or construction inputs. | Progression, survival, automation, trade. |
| Build | Place voxels, functional components, structures, roads, infrastructure or blueprint projects. | Settlement, movement, economy, defence. |
| Interact | Talk, inspect, trade, recruit, configure, transfer, accept, refuse, negotiate or command. | Social, economy, quest, automation. |
| Fight/Avoid | Attack, defend, flee, hide, negotiate, prepare or reroute. | Combat, survival, social, world history. |
| Repair/Maintain | Restore tools, machines, buildings, vessels, roads or biological condition. | Economy, crafting, settlement, survival. |

## 7.1 Responsiveness Before Abstraction

Even though Leyforge has civilisation-scale simulation, local interactions must remain direct. The player should feel that they are inhabiting a voxel world, not merely operating a strategy layer.

# 8. Hour-to-Hour Session Loop

A play session should naturally produce a sequence of self-chosen objectives.

A common rhythm is:

- notice a need or opportunity;
- plan a solution;
- travel or gather;
- process or negotiate;
- build, deliver, fight, trade or investigate;
- inspect the consequence;
- choose whether to deepen, pivot or leave.

The system should support sessions focused almost entirely on one activity, including:

- building;
- mining;
- farming;
- settlement work;
- trading;
- social play;
- exploration;
- dungeon delving;
- automation optimisation;
- magic research;
- shipbuilding;
- sea voyages;
- fishing;
- route construction;
- faction politics;
- combat;
- recovery and preparation.

No session needs to touch all pillars to be valid.

- biomes;

- ecological zones;
- sea routes;
- islands;
- underwater sites;
- realm anchors;
- hazards;

A ruin should not automatically mean "loot dungeon". It may be:

- monster or creature resources;

- buildings;

Knowledge can come from:

- experimentation;
- NPC teaching;
- books and records;
- ruins;
- factions;
- research;
- observation;
- quests;
- cultural knowledge;
- realm discovery.

## 12.1 Crafting Should Lead Outward

A recipe should usually enable something beyond the crafting screen:

- safer survival;

# 13. Building, Blueprint and Construction Loop

Building is both creative expression and functional world change.

> **Need/idea -> design or choose blueprint -> validate site -> acquire/reserve materials -> construct -> activate -> use -> maintain/repair/upgrade/transform**

The player may build through:

- direct voxel placement;
- modular pieces;
- player blueprints;
- official blueprints;
- NPC-assisted construction;
- settlement projects;
- infrastructure projects;
- vessel construction where governed by Set 26.

## 13.1 Function Requires More Than Appearance

Document 20 owns functional building contracts. A structure that visually resembles a clinic, warehouse, home or market does not automatically provide that service. Activation depends on the required semantic, access, staffing, resource, equipment, network, permission and condition state.

## 13.2 Player Creativity Remains First-Class

Functional validation must not remove freeform building. Decorative, personal and experimental construction remains legitimate even when it provides no settlement service.

# 14. Settlement and Civilisation Loop

Settlements are ongoing systems, not quest hubs waiting for the player.

> **Observe settlement -> understand needs/opportunities -> choose involvement -> contribute/exploit/ignore -> settlement responds -> new capacity/problems emerge -> history persists**

The seven main settlement needs remain:

- Housing;
- Provisions;
- Health;
- Work;
- Safety;
- Infrastructure;
- Morale.

These needs are high-level readability categories. They do not replace the detailed systems underneath them.

## 14.1 Ways to Engage

The player may:

- deliver goods;
- trade;
- build;
- repair;
- automate supply;
- recruit or teach specialists;
- improve transport;
- provide medicine;
- negotiate alliances;
- defend;
- investigate problems;
- establish businesses;
- fund public works;
- influence law or politics where permitted;
- exploit, threaten, occupy or conquer;
- leave the settlement alone.

## 14.2 Independent Settlement Life

Settlements may change without direct player action. Their growth is bounded by real population, services, resources, routes, safety, economy, knowledge and specialist availability. The player is a powerful catalyst, not the only thing keeping the world alive.

# 15. Automation, Logistics and Infrastructure Loop

Automation should convert repetitive physical labour into networks that create larger ambitions.

> **Identify repeated work -> build power/process/logistics -> connect inputs/outputs -> validate flow -> operate -> inspect bottleneck -> maintain -> scale -> integrate with civilisation**

Automation may support:

- extraction;
- farming;
- processing;
- sorting;
- storage;
- construction supply;
- trade stock;
- settlement provisions;
- defence supply;
- magical infrastructure;
- vessel yards;
- regional logistics.

## 15.1 Automation Does Not Create Resources

Goods, energy, mana and work remain authoritative. Distant simulation may batch outcomes but cannot fabricate throughput that the physical system could not support.

## 15.2 Infrastructure as Gameplay

Roads, bridges, storage, ports, rails, elevators, power networks, mana networks and transport links should matter because they change what people and goods can actually do.

# 28. Automation-to-Civilisation Escalation Loop

# 35. Simulation LOD and Off-Screen Continuity

Leyforge cannot physically simulate every person, item, creature, market and journey at full detail everywhere.

The loop therefore uses multiple simulation representations while preserving authoritative truth.

## 35.1 Near Simulation

Near the player:

- actors move physically;
- goods may be visible;
- construction is represented;
- combat is real-time;
- local pathing and interaction are detailed;
- machines expose direct operation.

## 35.2 Distant Simulation

At distance:

- settlements use bounded summaries;
- journeys retain semantic route progress;
- economic commitments persist;
- biological state uses approved cohort/actor summaries;
- social assignments persist;
- construction and production progress only when their owning rules permit;
- quantities cannot be fabricated by LOD.

## 35.3 Promotion/Demotion

When a distant system becomes local, the detailed state must reconcile from the authoritative summary rather than inventing a contradictory world.

# 36. Production Capability and Substitute-Path Rules

Set 25 establishes a capability-oriented production model so seeds and content packs do not depend on one exact item or structure.

Document 01 consumes that model through three gameplay rules.

## 36.1 Capability Before Exact Content

Where the game requires a capability, the world should prefer valid authored alternatives rather than hard-coded identity.

Examples:

- `basic cutting capability` may be provided by more than one approved tool/material family;
- `early shelter capability` may be satisfied by multiple building materials or found structures;
- `safe water crossing` may be solved by bridge, shallow crossing, swimming, vessel, magic or route detour depending on world state;
- `regional transport` may use road, mount, wagon, rail, vessel or other approved infrastructure.

## 36.2 Fallback Does Not Mean Free

A substitute must still obey:

- progression;
- resource availability;
- suitability;
- cultural/world context;
- gameplay balance;
- ownership/permissions;
- specialist-system validation.

## 36.3 Seed Reachability

A valid production seed should not trap the player because one exact POC-era item, village or ruin failed to generate.

The following kinds of capability remain valid unless explicitly superseded:

- persistent NPC identity;
- settlement warehouses;
- real resource delivery;
- staged construction;
- watchtowers and other defence buildings;
- hostile camps and threat sources;
- preparation changing danger outcomes;
- raids and aftermath;
- structure damage and repair;
- automation feeding storage/projects;
- mana/rune infrastructure where admitted by current registries;
- ruins and discovery;
- save persistence;
- simulation LOD;
- UI explanation and accessibility.

> **Preservation Rule**
>
> Remove the fixed demonstration dependency, not the gameplay capability that the demonstration happened to use.

# 38. Core Production Identity Proof

The production game needs a repeatable identity proof that does not recreate the POC.

Set 25 uses the **Living Frontier Network** as an internal non-canonical planning label for a dependency-complete production slice. Document 01 interprets that at player-experience level.

A valid Core Production identity proof should demonstrate, across one or more seed-generated relationships:

1. a player can spawn into a valid seed and form an early plan;
2. gathering and crafting create physical capability;
3. exploration reveals generated people, sites, resources or routes;
4. a settlement or comparable civilisation context has real needs and state;
5. the player can materially influence that state through at least several systems;
6. automation/logistics can scale a real production or supply problem;
7. magic can interact with the world beyond pure damage;
8. movement/routes materially affect access and logistics;
9. social interaction can create or change a meaningful opportunity;
10. economy can reflect real goods, demand, labour or transport;
11. danger/preparation can produce persistent consequence;
12. the world can save, load, promote/demote simulation and preserve history without depending on archived POC IDs.

Maritime or advanced realm systems may enter the Core identity proof according to Set 25 production classification rather than being automatically mandatory for the earliest releasable slice.

# 40. Balancing and Pacing Rules

## 40.1 Keep a Useful Next Action Visible

The player should usually be able to identify at least one meaningful next action without being forced into one specific task.

## 40.2 Alternate Intensity

Long-term play should naturally alternate between:

- tension and recovery;
- gathering and spending;
- discovery and consolidation;
- local work and travel;
- personal goals and civilisation goals;
- manual work and automation;
- danger and cosy creation.

## 40.3 Avoid Maintenance Overload

The game has many systems. Not all of them should demand attention simultaneously. Use:

- automation;
- delegation;
- configurable survival;
- quiet modes;
- summary UI;
- stable infrastructure;
- predictable maintenance intervals;
- NPC autonomy.

## 40.4 Preparation Should Matter

Equipment, information, routes, supplies, relationships and infrastructure should change the difficulty or cost of a challenge.

## 40.5 Avoid One Correct Build

Multiple combinations of:

- material;
- magic;
- social access;
- economy;
- movement;
- automation;
- combat;
- construction;
- companions;
- settlements

should remain viable.

## 40.6 Preserve Older Content Utility

Older materials, tools, buildings and routes remain useful where their cost, availability, repair role, cultural use, local suitability or specialised function justifies them.

# 41. Example Production Gameplay Stories

These examples are **non-canonical**. They demonstrate loop composition without creating fixed production content.

## 41.1 Mountain Settlement Supply Problem

A generated mountain settlement has adequate housing but poor provisions because a landslide damaged its road.

Possible player routes:

- clear and rebuild the road;
- create a temporary bridge or alternate path;
- use pack animals;
- establish a wagon route after improving terrain;
- negotiate an emergency supply contract;
- bring food manually;
- improve local farming;
- use approved magic to assist access or production;
- fund public works;
- ignore the problem and allow the settlement/economy to respond.

The important loop is not "deliver 20 food". It is **world condition -> multiple solutions -> persistent world/economic/social response**.

## 41.2 Coastal Salvage Opportunity

A storm exposes wreckage near a procedurally generated coast.

The player may:

- dive for salvage;
- hire or recruit help;
- use a small vessel;
- sell information;
- recover cargo under a contract;
- claim materials illegally and risk ownership consequences;
- ignore the site;
- investigate why the vessel sank.

The result can feed economy, crafting, maritime progression, social consequences, quests or faction history.

## 41.3 Companion Expedition

A companion shares a rumour about an inland ruin.

The player:

- decides whether to trust the information;
- plans a route;
- chooses supplies based on environment;
- travels with the companion;
- encounters a blocked passage;
- uses climbing, construction or an alternate route;
- explores the ruin;
- decides what to do with what is found;
- returns with changed knowledge and relationship state.

No one system owns the whole story. The loop is created by interfaces between them.

## 41.4 Industrial Expansion

A settlement's construction demand exceeds manual supply.

The player:

- identifies the bottleneck;
- secures a resource source;
- builds processing;
- automates transfer;
- improves transport;
- negotiates labour or business arrangements;
- supplies construction projects;
- sees the settlement grow;
- creates new demand for higher-capacity infrastructure.

Automation creates civilisation-scale goals rather than ending the resource game.

## 41.5 Threat Without Mandatory Combat

A hostile faction threatens a trade corridor.

The player may:

- fight;
- scout and avoid;
- fortify;
- negotiate;
- pay tribute;
- redirect caravans;
- support a rival faction;
- sabotage logistics;
- repair alternate roads;
- wait and accept economic consequences.

Different choices create different world histories.

# 43. Closing Direction

Leyforge's gameplay loop is not one chain of tasks. It is a **living network of causes, choices and consequences**.

The player begins by doing simple physical things in a voxel world: moving, gathering, crafting, building, eating, resting, observing and talking. Those actions gradually connect to people, settlements, machines, magic, roads, markets, companions, ships, factions, ecology, realms and history. The game becomes larger without abandoning the meaning of the small actions that created that growth.

The production standard is therefore:

> **The player should be able to understand what changed, why it changed, what they can do about it and what new possibility their action created.**

A seed may produce a mountain valley, an island chain, a forest frontier, a river basin, a hostile borderland or another valid production context. The exact content changes. The core fantasy does not.

**Explore. Gather. Craft. Build. Interact. Automate. Defend. Upgrade. Expand.**

And at every stage, let the world answer back.

# Appendix C. World-Response Checklist

For any major gameplay feature, ask:

- What authoritative world condition creates the opportunity/problem?
- How does the player learn about it?
- Can the player ignore it?
- Are there multiple plausible solution categories?
- Which specialist system owns validation?
- What real costs are committed?
- What world state changes?
- How is the result made visible?
- Which other systems consume the result?
- Does the world remember it after save/load?
- Can distant simulation preserve it without inventing resources or outcomes?
- Does the feature remain valid across different seeds?
- Does it accidentally depend on a retired POC identity?
- Is there a substitute/fallback capability where production reachability requires one?
- Does failure create a meaningful next state rather than only a reload?
