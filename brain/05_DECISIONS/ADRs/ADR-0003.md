# ADR-0003 — Leyforge and Zylann ownership and fork policy

## Context / Problem

The project needs an explicit boundary between upstream code, Leyforge adapters, patches and any maintained fork before production Zylann source or binaries are admitted.

## Accepted Decision

Use **upstream-owned Zylann plus Leyforge-owned adapters** as the default production ownership mode. Prefer a supported unmodified module or GDExtension edition when it satisfies the contract. Do not create a Leyforge fork or local upstream patch by implication.

Any required upstream modification or maintained fork must receive separate ADR coverage with base commit, patch identity, provenance, sync/update strategy, build reproduction, test obligations and exit plan. Direct edits to an unidentified upstream copy remain prohibited.

## Reconstruction Basis

B-OPS-06 and ENG-GOV-15 define the long-lived ownership and fork obligations. PRD-02 finds no specialist-system reason by itself to fork Zylann immediately, while PROD-03 preserves Leyforge semantic ownership above the voxel substrate. The owner accepted this default boundary on 26 September 2026; no fork or dependency activation is authorised by this decision alone.

## Reconsideration Triggers

- The owner approves, rejects or revises the proposed ownership mode.
- P01 demonstrates that supported extension surfaces cannot meet a required production contract.
- A local patch or fork becomes necessary.
